## Executive Summary

The original adversarial audit (docs/audits/11-03-2026-ADVERSARIAL-AUDIT.md) correctly identified 3 critical and 5 lower-severity issues. Of the fixes applied, **2 are correct, 1 is counterproductive, 1 is cosmetically correct but functionally negligible, and multiple config changes are dead code**. The most damaging error: `init_identity=False` was presented as a fix but empirically WORSENS the initialization compared to the correct fix (`tangent_scale` alone with identity init).

## Detailed Findings

### F1. `init_identity=False` Makes Initialization WORSE (CRITICAL)

**Claim by audit**: "Prevents the tangent_net from being initialized as identity (zero residual), allowing it to learn meaningful transformations"

**Reality**: This is backwards. Identity init is a standard residual network technique — it lets the network start as a no-op and gradually learn transformations. The `tangent_scale` addition was the actual fix for saturation.

**Empirical proof** (128 samples with actual encoder outputs, z_sample norm ~3.88):

| Configuration | Mean Norm | Std | >0.9 | Clamped at 0.95 |
|---------------|-----------|-----|------|-----------------|
| OLD: no scale + identity (committed code) | 0.9500 | 0.0000 | 100% | 100% |
| CORRECT FIX: scale=0.05 + identity | 0.1914 | 0.0350 | 0% | 0% |
| AUDIT'S FIX: scale=0.05 + non-identity | 0.8580 | 0.0459 | 14.1% | 0% |

**Full model forward pass** with audit's fix (TernaryVAEV6Controllable with 2 projection layers):

| Embedding | Mean Norm | Std | >0.8 | >0.9 |
|-----------|-----------|-----|------|------|
| z_A_hyp | 0.8792 | 0.0477 | 93.0% | 35.9% |
| z_B_hyp | 0.8705 | 0.0382 | 94.5% | 20.3% |

**Analysis**: With identity init + tangent_scale=0.05, points start at ~0.19 — squarely within the target range [inner_radius=0.08, outer_radius=0.70]. The tangent_net can gradually learn to spread points to the correct radii.

With non-identity init, the randomly initialized tangent_net (which includes LayerNorm → SiLU → Linear) produces outputs with significant norm that **dominate** the tiny scaled input (0.05 * 3.88 ≈ 0.19). Result: points start at ~0.88, **above** the target outer_radius of 0.70, and 93-95% are above 0.8.

**Root cause of audit error**: The audit tested `init_identity` in isolation (without tangent_scale), concluded identity was the problem, and didn't re-test after adding tangent_scale. The tangent_scale was the actual fix; toggling init_identity was unnecessary and counterproductive.

**tangent_scale gradient instability**: At initialization, `tangent_scale=0.05` receives gradients of magnitude ~10 (measured: 9.9 for proj_A, -13.2 for proj_B). With base_lr=8e-4 and projections_lr_scale=1.0, a single step changes tangent_scale by ~16%. This is concerning for training stability.

### F2. YAML Config Keys `init_identity` and `tangent_scale` Are Dead Config (HIGH)

The audit added these to v6.yaml:
```yaml
model:
  init_identity: false
  tangent_scale: 0.05
```

But `train.py` model construction at lines 251-267 never reads them:
```python
model = TernaryVAEV6Controllable(
    latent_dim=model_cfg.get("latent_dim", 16),
    hidden_dim=model_cfg.get("hidden_dim", 64),
    max_radius=model_cfg.get("max_radius", 0.95),
    curvature=model_cfg.get("curvature", 1.0),
    n_projection_layers=model_cfg.get("projection_layers", 2),
    projection_dropout=model_cfg.get("projection_dropout", 0.1),
    learnable_curvature=model_cfg.get("learnable_curvature", False),
    # ... NO init_identity or tangent_scale here
)
```

Furthermore, `TernaryVAEV6.__init__` does not accept `init_identity` or `tangent_scale` as parameters. Neither does `DualHyperbolicProjection.__init__`. The fix works ONLY because the Python default values in `HyperbolicProjection.__init__` were changed from `init_identity: bool = True` to `init_identity: bool = False` and the tangent_scale parameter was added with default 0.05.

**Impact**: Changing the YAML values has zero effect. Anyone editing the config to tune these parameters will be deceived into thinking their changes take effect. This is exactly the class of bug (dead config) that the original audit correctly flagged in C6 — and then the fix introduced the same class of bug for the new parameters.

### F3. KL Divergence Is Functionally Negligible (MEDIUM)

The audit correctly identified that KL divergence was missing (C4) and wired `HyperbolicKLDivergence` into CombinedLoss. However, the effective contribution is vanishingly small:

- `HyperbolicKLDivergence` applies `beta=0.1` internally (returns `0.1 * KL`)
- `CombinedLoss` applies `kl_weight=0.01` externally
- Effective weight: `0.01 * 0.1 = 0.001`
- With `free_bits=0.5` across 16 dimensions, minimum KL per sample = 8.0
- Minimum total KL contribution: `0.001 * 8.0 = 0.008` per sample

For comparison, `rich_hierarchy` loss with `hierarchy_weight=5.0` produces values in the range 0.1-10.0. The KL contribution is **~1000x smaller** than the dominant loss terms.

**Impact**: The model remains a nearly-deterministic autoencoder. The KL regularization is too weak to prevent posterior collapse. This isn't wrong per se (hierarchy structure is the priority), but it contradicts the audit's claim of "making this a true VAE."

### F4. Loss Doubling Has Implicit Hyperparameter Interaction (MEDIUM)

The train.py fix computes:
```python
loss = losses["total"] + losses_B["total"]
```

Both VAEs now compute ALL losses (hierarchy + coverage + geodesic + radial + monotonic + rank + KL). This approximately doubles the total loss magnitude. Combined with `max_grad_norm: 1.0` gradient clipping, the effective learning rate is halved whenever gradients are clipped.

**Impact**: The training dynamics change in a way that may require re-tuning of learning rate and gradient clipping threshold. This isn't a bug, but it's an unacknowledged side effect that could degrade training compared to simply fixing VAE-B gradient flow.

**Design question**: The CLAUDE.md says VAE-A is for "coverage" and VAE-B is for "hierarchy." But both now compute identical loss functions. The differentiation comes only from differential learning rates (encoder_a: 0.05x, encoder_b: 0.1x). This may be intentional but warrants explicit documentation.

### F5. Duplicate Line in Validation Loop (LOW)

`train.py` lines 1153-1154:

avg_val_acc = val_acc_sum / val_batches
avg_val_acc = val_acc_sum / val_batches  # duplicate

Harmless but indicates the validation section wasn't carefully reviewed after the changes.

## What the Original Audit Got Right

Credit where due — the original audit correctly identified:

1. **C1: VAE-B dead** — Verified. z_B_hyp was never used in loss computation. 0 gradient flow to 33/66 parameters. The fix (routing both z_A_hyp and z_B_hyp through CombinedLoss) is correct.

2. **C2: expmap0 saturation** — The diagnosis was correct. Encoder outputs with norm ~4.0 → tanh(4)=0.9993 → all points clamped at 0.95. The solution concept (scale down before expmap0) was correct, but the implementation paired it with an unnecessary and harmful init_identity change.

3. **C3: Config key mismatch** — Verified. `radial_weight` in YAML vs `weight` in code. Fix changing YAML to `weight: 5.0` is correct.

4. **C4: Missing KL** — Verified. CombinedLoss had no code path to compute KL. The wiring fix is structurally correct (adds mu/logvar params to forward, integrates HyperbolicKLDivergence), just underweighted.

5. **C5-C6: Dead config** — Verified. Multiple YAML keys had no corresponding code. Removal was correct.

6. **Mathematical verification** — The audit's finding that all math (3-adic valuation, ultrametric inequality, expmap/logmap composition) is correct was independently confirmed by the test suite (280 tests passing).

## Recommended Fix Strategy

### Priority 1: Revert init_identity to True

The `init_identity=False` change is counterproductive. With tangent_scale=0.05 handling the saturation issue, identity init gives superior initialization:
- Points start at ~0.19 norm (within target range [0.08, 0.70])
- Residual architecture allows gradual learning
- No random tangent_net output dominating the scaled input

**Action**: Change `init_identity: bool = False` back to `True` in `HyperbolicProjection.__init__` (or make it configurable by wiring from YAML through the model constructor).

### Priority 2: Wire init_identity and tangent_scale from config

Currently dead config. Either:
- (A) Remove the YAML keys and document that these are controlled by Python defaults only, OR
- (B) Wire them through: `train.py` → `TernaryVAEV6` → `DualHyperbolicProjection` → `HyperbolicProjection`

Option (B) is strongly preferred for a config-driven architecture.

### Priority 3: Decide on KL weight

Current effective weight of 0.001 makes KL negligible. Either:
- (A) Increase to meaningful level (e.g., weight=0.1 or beta=1.0 with weight=0.01 → effective 0.01)
- (B) Explicitly document that KL is intentionally negligible and hierarchy structure takes absolute priority
- (C) Remove KL entirely if it's not wanted (simplicity)

### Priority 4: Address loss doubling

Either:
- (A) Double max_grad_norm from 1.0 to 2.0 to compensate for doubled loss
- (B) Average instead of sum: `loss = (losses["total"] + losses_B["total"]) / 2`
- (C) Give VAE-A and VAE-B different loss compositions (e.g., VAE-B only hierarchy losses, no coverage)

### Priority 5: Clean up validation scripts

Remove ad-hoc scripts from repository root. If valuable, move tests to `tests/` with proper pytest structure.

## Tests Passing

All 280 tests pass with the current changes. However, the test suite does not cover:
- Config wiring (keys from YAML actually reaching the model)
- Initialization quality (distribution of initial embeddings)
- VAE-B gradient flow (no integration test for this)
- Loss magnitude / scale interactions

The test suite validates mathematical invariants and individual component behavior, but misses architectural integration issues. This is the same gap the original audit identified, and it remains unaddressed.
